# デモ台本：note.txt から設計書・コード・テストまで

Claude Code の5つの skill を実際に動かしながら説明するための台本です。各場面は次の3つで構成しています。

- **【操作】** 画面で行うこと、入力欄に打つ文
- **【話す】** そのまま読み上げてよい説明文
- **【見せる】** 画面で指し示す場所

所要時間の目安は **約40分**（設計書 約20分＋コード生成の紹介 約15分＋質疑）。コード生成は機能数によって30分〜1時間以上かかるため、**本番では事前に作っておいた結果を見せ、ライブでは開始部分だけを見せる**構成にしています（場面8）。

---

## 0. 事前準備（リハーサル時に必ず行う）

| # | 準備 | 確認方法 |
|---|---|---|
| 1 | `design_skill` を最新にする | `git pull` |
| 2 | Python 環境 | `./.venv/bin/python3 -c "import openpyxl, jsonschema"` がエラーにならない |
| 3 | `note.txt` が日本語のデモ用の内容になっている | `cat note.txt` |
| 4 | **前日までに、全工程（設計書5種＋コード生成）を一度通しで実行しておく** | `<システム名>/` に 02〜06 のフォルダと `07ソースコード_<日時>/` がある |
| 5 | 4 で起動したアプリにブラウザでログインできる | README に書かれた初期ユーザーでログイン |
| 6 | Excel（または WPS）を起動しておく | 生成した xlsx が開ける |
| 7 | ターミナルの文字を大きくする（会場の後ろから読めるサイズ） | `⌘ +` |
| 8 | Node.js が入っている | `node -v` |

**本番の直前に行うこと**

- `design_skill` ディレクトリで `claude` を起動し、入力欄で `/` を打って5つの skill（`requirements-definition` / `basic-design` / `detailed-spec` / `detailed-design` / `code-generation`）が出ることを確認する。
- 本番でライブ生成する場合は、リハーサルの `<システム名>/` フォルダを別名（例: `<システム名>_リハーサル`）に変えておく。残したままだと「既存の主表を使う」動きになり、要件定義から作り直す様子が見せられない。
  - 作り直すと全く同じ内容になるとは限らない。リハーサル版は場面8・9の「完成品」として使うので、**削除はしない**。
- ブラウザのタブを2つ開いておく: リハーサルで起動したアプリと、空のタブ。

## 1. オープニング（2分）

**【見せる】** ターミナル（`design_skill` で Claude Code を起動した状態）

**【話す】**

> 本日は、Claude Code を使って、システムの概要メモから日本の SI で使う設計書一式を作り、さらにその設計書どおりにプログラムとテストまで作る流れをご覧いただきます。
>
> 設計書の作成には、いつも3つの悩みがあります。1つ目は、決まった書式を埋める作業に時間がかかること。2つ目は、要件定義書・基本設計書・詳細設計書で、機能名や ID が少しずつずれていくこと。3つ目は、設計書と実際のプログラムが一致しなくなることです。
>
> 今日お見せする仕組みは、この3つを、決まった手順を持つ「skill」で解決します。

## 2. 全体の流れ（2分）

**【見せる】** 次の図をスライドかホワイトボードで（またはこの台本を画面に表示）

```
note.txt（数行の概要）
   │
   ▼
要件定義書 → 基本設計書 → 詳細仕様書 → 詳細設計書 → コード＋テスト＋テスト結果報告書
 (システム1冊)  (機能ごと)    (機能ごと)    (画面ごと)    (アプリを起動して URL を表示)
   └──────────── すべて「設計主表」の ID で対応づけ ────────────┘
```

**【話す】**

> 工程は5つで、それぞれが1つの skill になっています。順番は固定です。上流の設計書が無いのに下流を作ろうとすると、スクリプトが止めます。
>
> ポイントは「設計主表」です。最初に、要件・機能・画面・API・テーブル・メッセージに ID を振った一覧を作ります。以降の設計書はすべて、この一覧の ID と名前だけを使って書かれます。ですから、文書によって名前が違う、ということが起きません。
>
> 生成されたファイルは、すべてこのプロジェクトのフォルダの中に、システム名のフォルダを作って保存されます。ファイル名の最後には生成した日時が付くので、作り直しても前の版は消えずに残ります。

**【操作】** 別のターミナル（または Claude Code の入力欄で `! cat note.txt`）

```
! cat note.txt
```

**【見せる】** 「目的・背景」「技術スタック」「機能・画面」の3か所

**【話す】**

> 入力はこのテキストファイルだけです。ご覧のとおり、書いてあるのは十数行です。ツリー構造でノードを管理する Web システムで、技術は Next.js と SQLite、画面はログイン、トップ画面、ノードの登録・更新・削除です。
>
> 非機能要件、テーブル定義、エラーメッセージなどは書いていません。書いていない部分は、skill がシニア設計者の立場で、この概要と矛盾しないように決めます。決めた前提は、あとで「要確認項目」として一覧で出てくるので、そこだけ人が確認します。

## 4. 要件定義書（5分）

**【操作】** 入力欄に打つ

```
要件定義書を作成して
```

**【話す】（実行が始まったら）**

> 依頼はこの一言です。skill は最初に note.txt を読み、システム全体を設計して、設計主表を作ります。

**【見せる】** Claude が表示する ID の一覧（REQ-xxx、F-xx、SCR-xx、IF-xx、TBL-xx、MSG-xxx）

**【話す】**

> これが設計主表の中身です。要件には REQ、機能には F、画面は SCR、API は IF、テーブルは TBL、メッセージは MSG の番号が振られています。この後の設計書は、すべてこの番号で書かれます。

**【待ち時間のトーク】**（1〜3分）

> いま裏では、決まった順番の処理が動いています。設計書の中身を JSON という形式で書き、決められた構成どおりかをチェックし、設計主表に無い ID を使っていないかをチェックし、最後に Excel を作ります。チェックで問題が見つかると、skill が自分で直してやり直します。人が途中で答える必要はありません。

**【見せる】** 完了メッセージの次の部分

- 出力した Excel のパス（`02要件定義/<システム名>_<日時>.xlsx`）
- 「要確認項目」（NOTES_FOR_REVIEW）
- 「未作成」の文書一覧

**【操作】** Excel でファイルを開き、シートを順に見せる: 表紙 → 改定履歴 → 目次 → 各章

**【話す】**

> 会社の様式どおりの表紙、改定履歴、目次が付いています。罫線や方眼紙のレイアウトは、社内のテンプレートをそのまま使っています。
>
> 要件の表には REQ の番号が振られています。この番号は、後の基本設計書や詳細設計書にもそのまま出てきます。
>
> 業務フロー図のような図は、自動では作りません。図が入る場所には「別途図を貼付」という注記が入るので、そこは手で貼っていただきます。

## 5. 基本設計書・詳細仕様書（5分）

**【操作】**

```
基本設計書を作成して
```

**【話す】**

> 基本設計書は機能ごとに1冊です。対象を指定しなければ、まだ作っていない機能の分をまとめて作ります。基本設計書は、要件定義書の内容を読んで、それに合わせて書かれます。

**【待ち時間のトーク】**

> 機能の数だけ繰り返すので、少し時間がかかります。この間に、順番を守らないとどうなるかをお話しします。例えば、基本設計書が無いのに詳細仕様書を作ろうとすると、スクリプトが「先に基本設計書を作成してください」と止めます。上流の決定を読まずに下流を書く、ということが起きない仕組みです。
>
> 順番だけではありません。例えば詳細設計書の入力チェックで、名称の桁数を詳細仕様書と違う値で書くと、スクリプトが「詳細仕様書では100桁」と指摘して、Excel を作りません。メッセージの文言、API の URL なども同じように上流と突き合わせています。

**【見せる】** Finder（またはターミナル）で `03基本設計/` フォルダ。ファイル名の `F-01_<機能名>_<日時>.xlsx`

**【話す】**

> ファイル名の最後が生成した日時です。同じ設計書をもう一度作ると、別の日時のファイルとして増えます。上書きされないので、前の版との比較ができます。

**【操作】**

```
詳細仕様書を作成して
```

**【話す】**

> 詳細仕様書も機能ごとに1冊です。画面項目、桁数、必須かどうか、エラーメッセージなど、プログラムを作るのに必要な細かい仕様をここで決めます。

（待ち時間が長い場合は、場面7のトレーサビリティマトリクスを先に見せてもよい）

## 8. コードとテストの生成（ライブは開始部分だけ・5分）

**【操作】**

```
設計書からコードを生成して
```

**【話す】**

> 最後の工程です。設計書が全部そろったので、この設計書どおりにプログラムを作ります。コードもこのプロジェクトの中に、「07ソースコード」と日時の付いたフォルダを新しく作って書かれます。

**【見せる】** Claude が最初に行う「設計書レビュー」の出力

**【話す】**

> いきなりコードを書くのではなく、まず詳細仕様書と詳細設計書をレビューします。画面項目の桁数、メッセージの文言、API の項目名などが文書の間で食い違っていないかを突き合わせます。重大な矛盾があれば、設計書を先に直すか、どう解釈して進めるかを人に確認します。
>
> レビューが終わると、共通部分を作ってから、機能を1つずつ作ります。機能ごとにテストを書いて実行し、テストが通ってから次の機能に進みます。

**【話す】（ここでライブを切り替える）**

> 全部の機能を作るには30分から1時間ほどかかります。今日は、事前に同じ手順で最後まで作ったものをお見せします。

（ライブの処理は止めずに裏で動かしておいてよい。止める場合は `Esc`）

**【見せる】** リハーサルの `07ソースコード_<日時>/` フォルダ

- `README.md`（起動方法・テスト方法・初期ユーザー）
- ソースファイル先頭のコメント（`// F-05 ノード登録機能 / IF-06 POST /api/nodes / SCR-03` のように、設計書の ID が書かれている）
- テストファイル（テスト名の先頭に `TC-05-003` のようなテスト ID）

**【話す】**

> プログラムの各ファイルには、どの設計書のどの機能・API・画面を実装したものかが ID で書かれています。設計書からプログラムへ、プログラムから設計書へ、どちらからでもたどれます。
>
> テストは、画面や API を外から動かして確かめる機能テストです。全機能について、正常なケースと異常なケースを必ず含め、設計書に出てくる全 API と全メッセージを、どこかのテストで確認しています。足りないと、スクリプトがテスト結果報告書を作らずに止めます。

## 10. テスト結果報告書（3分）

**【操作】** Excel で `06テスト結果/<システム名>_テスト結果報告書_<日時>.xlsx` を開く

**【見せる】** 1章「テスト概要」の結果サマリ（機能ごとの件数・OK・NG・未実施）→ 2章「テスト結果一覧」→ 4章「設計書レビュー結果」

**【話す】**

> テスト結果報告書です。ここに書かれた OK・NG は、AI が書いたものではありません。テストを実際に実行したときに、テストツールが出力した結果ファイルから転記しています。テストケースの一覧には結果を書く欄そのものが無いので、AI が「成功しました」と書き換えることはできません。失敗したテストがあれば、失敗のままここに載ります。
>
> 4章には、コードを作る前に行った設計書レビューの指摘と、実装でどう扱ったかが残ります。設計書の直すべき点も、ここから分かります。

**【操作】** トレーサビリティマトリクスをもう一度開き、「テスト結果」列を見せる

**【話す】**

> トレーサビリティマトリクスにもテスト結果の列が加わりました。要件から、機能、設計書、テスト結果までが1枚でつながります。

**【話す】**

> まとめます。
>
> 1つ目、入力は数行の概要だけで、会社の様式どおりの設計書が一式できます。

## 想定質問と回答

| 質問 | 回答 |
|---|---|
| 生成された設計書の品質は、そのまま納品できるレベルか | 骨格と書式は社内テンプレートどおりで、内容も概要と矛盾しないように書かれます。ただし、AI が決めた前提は「要確認項目」として出るので、そこは必ず人が確認します。図も手で貼ります。レビュー前の初版として使うのが前提です。 |
| 概要を直したらどうなるか | note.txt に書き足して依頼し直せば、設計主表ごと直してから設計書を作り直します。Excel は日時付きの新しいファイルになり、前の版も残ります。 |
| 文書の間の不整合は本当に起きないのか | スクリプトが3段階で検査します。1つ目は作成順序、2つ目は ID（主表に無い ID や、書くべき ID の抜け）、3つ目は内容です。内容では、メッセージの文言、API の URL、画面項目の必須・桁数、サブ機能の構成などを上流の文書と突き合わせ、1つでも違えば Excel を作りません。上流を作り直した場合は、合わなくなった下流の文書が一覧に出ます。文章で書かれた処理の考え方のような機械で比べられない部分は、コード生成の前のレビューで確認します。 |
| 別の技術スタックでも使えるか | note.txt の技術スタックに書けば、設計内容もコードもそれに合わせます。Java、Python なども可能です。 |
| テストが失敗したらどうなるか | 機能ごとに最大5回まで原因を調べて実装を直します。それでも通らなければ、失敗のまま報告書に残し、レビュー結果にも記録します。テストを外したり、期待値を書き換えたりはしません。 |
| 既存のシステムに機能を追加できるか | 現在は対象外です。コードは毎回新しいフォルダに作ります。 |
| 社外に情報が出ないか | 生成物はすべてこの PC のプロジェクトフォルダに保存されます。Claude との通信は、会社で契約している Claude Code の利用条件に従います。 |

## うまくいかないときの対応

| 症状 | 対応 |
|---|---|
| skill が `/` の候補に出ない | `design_skill` ディレクトリで `claude` を起動し直す |
| 権限の確認が出た | 内容を読み上げて「許可」を選ぶ（「ファイルへの書き込みや、テストの実行の前には、このように人の確認が入ります」と説明に使える） |
| 生成に時間がかかりすぎる | リハーサルで作った完成品に切り替えて説明を続ける |
| アプリが起動しない／ポートが使用中 | リハーサルで起動しておいたアプリのタブに切り替える。後で `lsof -iTCP:3000 -sTCP:LISTEN` で確認する |
| Excel のレイアウトが崩れて見える | 表示倍率を変える。WPS の場合は Excel で開き直す |
