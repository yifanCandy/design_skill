# 設計主表ルール（5つの skill 共通）

1つのシステムの 要件定義書・基本設計書・詳細仕様書・詳細設計書 を互いに対応させるため、全文書は **設計主表 `<設計フォルダ>/master.json`** に定義された ID・名称だけを使って書く。各文書が `note.txt` から個別に推測して命名することはしない。

**`<設計フォルダ>` = `<プロジェクト>/<システム名>/_design`**。`<プロジェクト>` は**このリポジトリのディレクトリで固定**（変更できない）。システムごとに `<システム名>/` フォルダを作ってその中に全文書とコードを書く。実際のパスは `./.venv/bin/python3 scripts/traceability.py systems` で確認する（`DOC_ROOT` 行がプロジェクトディレクトリ、`SYSTEM` 行が既存システムの主表パス）。

**生成する Excel のファイル名には必ず `_<日時>`（`YYYYMMDDHHMMSS`）が付く。** 生成のたびに新しいファイルになり、以前に生成したファイルは上書きされずに残る（同じ文書の版の比較ができる）。トレーサビリティマトリクスだけは日時を付けず、生成のたびに最新の状態に更新する。

## 1. ファイル配置

```
note.txt                                               ユーザーが書く需求概述（git管理外）
<プロジェクト>/<システム名>/
├── _design/                                   設計フォルダ（Excel を開く人は触らない）
│   ├── master.json                            設計主表（スキーマ: templates/_shared/master.schema.json）
│   ├── requirements-definition/requirements.json
│   ├── basic-design/F-xx.json                 機能ごとに1つ
│   ├── detailed-spec/F-xx.json, SCR-xx.json   ツール仕様書（機能ごと）、画面定義書骨格（要望時のみ）
│   ├── detailed-design/SCR-xx.json            画面ごとに1つ
│   └── code-generation/tests.json             テストケース台帳と設計書レビュー結果（code-generation skill）
├── 02要件定義/ 03基本設計/ 04詳細仕様/ 05詳細設計/ 06テスト結果/   生成された Excel（この順に作る。ファイル名は …_<日時>.xlsx）
├── 07ソースコード_<日時>/                     code-generation skill が生成したアプリ（生成のたびに新しいフォルダ）
└── <システム名>_トレーサビリティマトリクス.xlsx
```

**作成順序は 要件定義書 → 基本設計書（F ごと）→ 詳細仕様書（F ごと）→ 詳細設計書（SCR ごと）→ コード・テスト結果報告書（システムで1つ、`code-generation` skill）で固定。** 下流の文書は、上流の文書の content.json を Read して、そこで決めた内容（機能構成、画面項目、メッセージ、動作）と矛盾しないように書く。`generate.py` は上流が無いと終了コード3（`PREREQUISITE MISSING`）で止まる。

| 作る文書 | 先に必要な文書（Read して従う） |
|---|---|
| 基本設計書 F-xx | 要件定義書（`requirements-definition/requirements.json`） |
| 詳細仕様書 F-xx | 同じ F の基本設計書（`basic-design/F-xx.json`） |
| 詳細設計書 SCR-xx | その画面の**全 F** の詳細仕様書（`detailed-spec/F-xx.json`） |
| コード・テスト結果報告書 | 全 F の詳細仕様書と全 SCR の詳細設計書 |

**content.json のファイル名は必ず対象の ID（要件定義書だけは `requirements`）にする。** `generate.py` はファイル名と親フォルダ名から対象と文書種別を判定し、主表との整合を検査する。

## 2. 主表を用意する（各 skill の手順1）

1. **需求概述の取得元**（優先順）: ①会話に概述が書かれていればそれ ②ファイルパスを渡されたらそのファイル ③リポジトリ直下の `note.txt`。どれも無い・空なら「`note.example.txt` をコピーして `note.txt` を作り、数行で概要を書いてから、もう一度依頼してください」とだけ伝えて止まる。
2. **対象システムの特定**: `./.venv/bin/python3 scripts/traceability.py systems` を実行し、既存の主表を確認する。
   - 1つも無い → 3. で新規作成する。
   - 概述のシステム名、または概述の内容と一致する主表があれば、それを使う。複数の候補があって決められない時だけ AskUserQuestion で聞く。
3. **新規作成**: 概述からシステム全体を設計し、スキーマに従って `<設計フォルダ>/master.json` を Write する（`NEW_SYSTEM_MASTER` 行のパスの `<システム名>` を置き換えたもの）。
   - `system.name` が概述に無ければ内容から日本語で命名する。`note_snapshot` には使った概述の全文を入れる。
   - 概述に書かれていない要件・機能・画面・IF・テーブル・メッセージは**ユーザーに聞かず**、シニア設計者として概述と矛盾しない範囲で設計する。技術スタックが書かれていればそれに合わせる（例: Next.js なら IF は Route Handler の `/api/...`）。
   - 粒度の目安: 要件（REQ）は機能要件と非機能要件の両方を含め10〜20件。機能（F）は利用者から見た機能単位（ログイン機能、ノードツリー表示機能など）で、1つの F が1冊の基本設計書・1冊の詳細仕様書になる。画面（SCR）は1画面1つで、1つが1セットの詳細設計書になる。
   - 非機能要件の REQ は、それを主に担う F に割り当てる（全機能共通のもの、例えばセキュリティ全般は、認証系の F に割り当てる）。どの F からも参照されない REQ を残さない。
   - 決めた前提（命名、数値目標、データ項目、対象外にしたもの）は `assumptions` に書く。
   - 書いたら `./.venv/bin/python3 scripts/traceability.py check-master <設計フォルダ>/master.json` を実行する。エラーが出たら自分で直して再実行する。成功したら表示された ID 一覧をユーザーに見せ、そのまま手順2へ進む（確認待ちはしない）。
4. **既存の主表を使う場合**: 現在の概述と `note_snapshot` を比べる。
   - 同じ → そのまま使う。
   - 違う → 概述の変更点から主表への変更案（追加する ID、名称・説明を変える ID）を箇条書きで示し、AskUserQuestion で了承を得てから更新する。`note_snapshot` も更新し、`check-master` を実行する。
5. **主表の不変ルール**
   - **ID は追記のみ。** 既存 ID の改番・削除・別物への流用はしない。不要になった要素は削除せず、name の先頭に「（廃止）」を付ける。
   - 名称を変える時は主表だけを変え、作成済み文書は次回生成時に追随させる。
   - 下流の文書を書いていて主表に無い要素（新しい IF、メッセージなど）が必要になったら、**先に主表へ次の番号で追記し、`check-master` を通してから**文書に書く。文書だけに新しい ID や名称を書かない。
   - **主表は共有ファイル**（他のメンバーが同時に追記している可能性がある）。追記の直前に必ず Read し直し、その時点の最大番号の次を採番し、Write で全体を書き換えずに Edit で該当配列に要素を足す。`check-master` で ID 重複が出たら、自分が足した側を次の空き番号に振り直す。
   - 同じ文書を作り直す場合は、既存の `<設計フォルダ>/<skill名>/<ID>.json` を直して再生成する（確認は不要。Excel は日時付きの新しいファイルになり、以前の版は残る）。

## 3. 文書ごとの対象と、必ず書く ID

ID は本文中にそのまま書く（例:「【REQ-003】ノードツリーの…」「IF-02 GET /api/nodes/{id}」）。`generate.py` が本文中の ID を拾い、主表に無い ID と、下表の「必ず言及する ID」の欠落をエラー（終了コード1、`TRACE FAILED`）にする。さらに、下の文書ごとの規則のうち **【検査】** と付いたものは `scripts/consistency.py` が主表・上流の文書と内容を突き合わせ、違えばエラー（終了コード1、`CONSISTENCY FAILED`）にする。表の列名は検査に使うので、規定の列名をそのまま使う。

| 文書 | 対象（ファイル名） | meta.function_name | 必ず言及する ID |
|---|---|---|---|
| 要件定義書 | システム全体（`requirements`） | システム名 | 全 REQ |
| 基本設計書 | F ごと（`F-xx`） | `F-xx_<機能名>` | 対象 F と、その F の REQ |
| 詳細仕様書 | F ごと（`F-xx`） | `F-xx_<機能名>` | 対象 F、その F を含む SCR、その F のメッセージ |
| 画面定義書骨格 | SCR ごと（`SCR-xx`） | `SCR-xx_<画面名>` | 対象 SCR |
| 詳細設計書 | SCR ごと（`SCR-xx`） | `SCR-xx_<画面名>` | 対象 SCR、その画面の IF、その画面の機能のメッセージ |
| テスト結果報告書 | システム全体（`code-generation/tests.json`） | システム名 | 全 F・SCR・IF・MSG（テストケースの対象として） |

全文書共通: `meta.system_name` は主表の `system.name` と完全一致させる。作成者は `git config user.name`、作成日は今日。用語は主表の `glossary` の表記に揃える。

### 要件定義書
- 1.4 用語定義 = 主表の `glossary`。
- 3章の要件一覧 = 主表の全 REQ。列は `['No','要件ID','要件名','概要','分類','優先度','対応機能']`、対応機能には担当 F の ID と名称を書く。【検査】全 REQ が1行ずつあり、要件名が主表どおり、対応機能の F が主表どおり。
- 4章の非機能要件の各行は、該当する非機能 REQ を「【REQ-xxx】…」の形で書く。

### 基本設計書（F ごと）
- 要件定義書（`<設計フォルダ>/requirements-definition/requirements.json`）を Read し、この F の REQ の記述と矛盾しないように書く。
- 1.1 参照資料に「<システム名> 要件定義書（REQ-xxx, …）」を入れる。
- 3章の各要件は、この F の REQ を分類ごとに「【REQ-xxx】…」で書く。この F に無い分類は、システム共通の定型文でよい。【検査】文書全体で、この F の REQ 以外の REQ ID を書かない。
- 4章のサブ機能では、関係する画面・IF を「SCR-xx」「IF-xx」で示す。
- 6章は、この F が使うテーブル（TBL）の項目定義、またはこの F の IF の入出力形式を書く。項目名・型は主表の `columns` と一致させる。

### 詳細仕様書（F ごと）
- 4章のツール機能は、基本設計書の同じ F の4章と同じサブ機能構成にする（`<設計フォルダ>/basic-design/F-xx.json` を Read して揃える）。【検査】サブ機能の見出し（title）が基本設計書4章と同じ順・同じ文字列。
- 6章の画面定義には、この F を含む画面を「SCR-xx <画面名>」の名前で載せる。項目定義表の列には `日本語名`・`必須`（必須なら ○、任意なら空か -）・`桁数` を必ず含める（例: `['No','日本語名','タイプ','読取','必須','桁数','初期値','備考']`）。【検査】画面がこの F を含む SCR と過不足なく一致。同じ画面を載せている作成済みの他の F の詳細仕様書と、同じ日本語名の項目の必須・桁数が一致（先に作られた方に合わせる）。
- 9章のエラーメッセージには、この F の MSG を ID と文言そのままで載せる。表の列は `['メッセージID','区分','メッセージ']`。【検査】この F の MSG が過不足なくあり、区分・文言が主表と一致。

### 詳細設計書（SCR ごと）
- その画面の F の詳細仕様書（`<設計フォルダ>/detailed-spec/F-xx.json`）をすべて Read し、6章の画面項目・7章の動作・9章のメッセージを処理ステップに落とす。詳細仕様書と異なる動作を新たに決めない（変える必要があれば先に詳細仕様書を直す）。
- IF定義書のシナリオは、この画面の IF ごとに作る。`process_name` は「IF-xx <IF名>」、通信方式と URL は主表の method・path をそのまま使う。【検査】シナリオの IF がこの画面の IF と過不足なく一致し、process_name・通信方式・URL が主表どおり。
- 詳細設計書本体の処理ステップでは、呼び出す IF・参照するテーブルを ID で示す。
- 入力チェックの処理ステップには、列 `項目名`・`必須`・`桁数` を含む表（例: `['項目名','必須','桁数','チェック内容','メッセージID']`）を置き、画面の入力項目を詳細仕様書6章の日本語名・必須・桁数のまま載せる。【検査】表の項目がすべて詳細仕様書6章のこの画面にあり、必須・桁数が一致。詳細仕様書で必須の項目が全部載っている。
- メッセージID一覧は、この画面の機能のメッセージ（MSG）をすべて載せる。列は `['#','定義場所','メッセージID','ツール仕様書のエラーID','備考']`、「ツール仕様書のエラーID」列にも同じ MSG-xxx を書く（詳細仕様書の9章と1対1で対応させるため）。【検査】この画面の機能の MSG が過不足なくあり、2つの ID 列が同じ。

## 4. 生成後

`generate.py` は成功するたびに `<プロジェクト>/<システム名>/<システム名>_トレーサビリティマトリクス.xlsx` を更新し、まだ作られていない文書（`NOT_YET_CREATED`）と不整合（`TRACE_ISSUE`）を表示する。`TRACE_ISSUE` は、作成済みの文書がいまの主表・上流の文書と合わなくなったもの（上流を作り直した後の下流など）。**表示されたら、その文書名と内容を報告し、作成順序どおり（上流から）作り直すよう伝える**（例:「基本設計書 F-01 の4章を変えたので、詳細仕様書 F-01 → 詳細設計書 SCR-01 の順に作り直してください」）。報告の最後に、まだ作成されていない文書を1行で伝える（例:「未作成: 基本設計書 F-02, F-03 / 詳細仕様書 F-02 / 詳細設計書 SCR-02」）。
